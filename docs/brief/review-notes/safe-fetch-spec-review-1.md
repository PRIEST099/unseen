# Claude Code review: safe-fetch spec (before implementation)

Date: 2026-11-24. Method: 2 reviewers (attacker view / SSRF completeness, and engineering feasibility with Playwright and Chromium), each followed by a skeptical verifier. Several findings were checked against Playwright 1.65.1 source and Node 24. **30 confirmed findings**; 3 rejected.

## 1. [blocker] .kiro/specs/safe-fetch/design.md:237 (ssrf-completeness)

**Issue:** Chromium sends some requests around the proxy. Clause 2.14 (and task 12) only adds a raw `--proxy-server=127.0.0.1:<port>` argument. Chromium's implicit bypass rules then connect directly to localhost, *.localhost, 127.0.0.0/8, [::1], 169.254.0.0/16 and fe80::/10. That means `fetch('http://169.254.169.254/...')`, `fetch('http://127.0.0.1:<any>/')`, `new WebSocket('ws://127.0.0.1:8080')` and redirects to those addresses never reach the proxy. Design 2.37 and task 12 step 5 also drop page.route in restrictive mode, so nothing checks those requests at all. The cloud metadata endpoint becomes reachable.

**Evidence:** Playwright 1.65.1 (node_modules/playwright-core/lib/coreBundle.js, crBrowser.ts) adds `<-loopback>` only when its own `proxy` option is used: `if (shouldProxyLoopback(proxy.bypass)) proxyBypassRules.push("<-loopback>")`, both in _innerDefaultArgs and in doCreateNewContext. Arguments passed through `args` (how buildLaunchArgs' extraArgs is used) are not processed. The spec never mentions `--proxy-bypass-list` or `<-loopback>`. Tasks 5 and 19 audit loopback URLs, so with the implicit bypass they would exercise a direct connection, not the proxy.

**Fix:** Replace design 2.14 with: "WHEN a restrictive audit creates its BrowserContext THEN the system SHALL pass `proxy: { server: 'http://127.0.0.1:<proxy-port>', bypass: '<-loopback>' }` to `browser.newContext()` in `PageLoader.createContext`. The bypass value is set explicitly so it does not depend on PLAYWRIGHT_DISABLE_FORCED_CHROMIUM_PROXIED_LOOPBACK. No host is ever bypassed." Add to tasks 12 and 15 an integration test. A page served through the proxy calls fetch() to http://127.0.0.1:<live port>/, http://localhost:<live port>/, http://[::1]:<live port>/ and http://169.254.169.254/. Each must appear in blockedRequests, and the live loopback server must record zero hits.

**Verifier note:** Confirmed: design 2.14 and task 12 pass only a raw `--proxy-server` argument, and Playwright 1.65.1 adds `<-loopback>` only for its own `proxy` option (coreBundle.js:40109-40115, 40864). Chromium's implicit bypass therefore sends loopback, 169.254/16 and fe80::/10 directly, and in restrictive mode no page.route remains to catch them.

## 2. [blocker] .kiro/specs/safe-fetch/design.md:831 (ssrf-completeness)

**Issue:** The proxy is chosen with `policy instanceof RestrictiveSafeFetchPolicy`, and that check is false on every real code path. PageLoader.load receives `meter.wrapPolicy(policy)`, a plain object. auditHtml and auditSite pass `OriginScopedPolicy`, and callers can supply `options.safeFetchPolicy`. So every hosted audit takes the page.route-only branch. That leaves DNS pinning, redirect checks and WebSocket checks out, which are the bypasses this spec exists to close.

**Evidence:** audit.ts:153 `parts.loader.loadPage(parts.context, url, meter.wrapPolicy(policy), ...)`. resource-limits.ts `wrapPolicy` returns `{ shouldBlock: async (url) => ... }`, not a class instance. audit.ts:328 wraps in `new OriginScopedPolicy(origin, selectPolicy(options))`. Design 2.36, 2.37 and task 14 branch on `instanceof RestrictiveSafeFetchPolicy` / `instanceof PermissiveSafeFetchPolicy`.

**Fix:** In design 2.36/2.37 and task 14, replace the instanceof dispatch with an explicit mode that fails closed. Add `readonly mode?: 'restrictive' | 'permissive'` to SafeFetchPolicy. RestrictiveSafeFetchPolicy sets 'restrictive', PermissiveSafeFetchPolicy sets 'permissive', and ResourceMeter.wrapPolicy and OriginScopedPolicy forward `inner.mode`. Add the sentence "The proxy SHALL be used unless `policy.mode === 'permissive'`. A policy with no mode is treated as restrictive." Add a test: auditUrl with default options must create its context with a proxy, asserted by a spy on browser.newContext options or by a loopback fetch being blocked.

**Verifier note:** Confirmed: audit.ts:153 passes `meter.wrapPolicy(policy)`, a plain object literal (resource-limits.ts:45-62), and auditHtml wraps the policy in OriginScopedPolicy, so the `instanceof RestrictiveSafeFetchPolicy` dispatch at design.md:831 and in task 14 is never true and the proxy branch never runs.

## 3. [blocker] .kiro/specs/safe-fetch/design.md:673 (ssrf-completeness)

**Issue:** The proxy handles only CONNECT. Through an HTTP proxy, Chromium sends plain http:// navigations, subresources and redirect hops as absolute-form requests (`GET http://host/path HTTP/1.1`). The server has no 'request' listener, so those requests hang, or an implementer later adds a naive forwarder. No text says which authority to resolve: the request-line authority or the attacker-controllable Host header. Nothing says how to treat origin-form requests or `Upgrade` requests either. Clause 2.16 mentions an 'HTTP request', but no handler is ever specified.

**Evidence:** design.md:673 `this.server.on('connect', this.handleConnect.bind(this))` is the only listener. Task 11 says 'Create `http.createServer()` with `'connect'` event handler' only. The redirect tests (tasks 5 and 18) are all plain http://, so they depend on the missing path.

**Fix:** Add to design §3 and task 11: "The proxy SHALL handle 'request' events. It SHALL accept only absolute-form `http://` request targets, and SHALL answer 400 to origin-form or other schemes. It SHALL take host and port only from the request-target URL, never from the Host header. It SHALL run the same resolve, classify and pin step as CONNECT, connect to the pinned IP, and overwrite Host with the request-target authority. It SHALL strip Proxy-* and hop-by-hop headers, and SHALL NOT follow redirects itself; Chromium re-requests each hop through the proxy. 'upgrade' events SHALL be rejected with 400, because Chromium tunnels ws:// over CONNECT." Add unit tests for: Host header 127.0.0.1 with a public request-target, where the request must go to the public pinned IP; an origin-form request, which must get 400; and an absolute http://127.0.0.1/ request, which must get 403 and be logged.

**Verifier note:** Confirmed: the server registers only a 'connect' listener (design.md:673, task 11), so absolute-form `GET http://...` requests that Chromium sends for plain-http navigations, subresources and redirects get no handler and hang, and the redirect tests depend on exactly that path.

## 4. [blocker] .kiro/specs/safe-fetch/design.md:704 (ssrf-completeness)

**Issue:** Every HTTPS CONNECT crashes the Node process. `new URL('https://host:443/').port` is '' because the default port is dropped, so `parseInt` gives NaN. `net.connect(NaN, ip)` then throws ERR_SOCKET_BAD_PORT synchronously inside the async 'connect' handler. That is an unhandled rejection, which ends the process on Node 24. The tunnel also has no clientSocket 'error' listener, and Node removes the server's socketOnError after 'connect', so a reset from Chromium also crashes the hosted server and every concurrent audit with it.

**Evidence:** Verified on this machine (Node v24.11.1): `new URL('https://example.com:443/').port` gives `''`, `parseInt('',10)` gives NaN, and `net.connect(NaN,'1.1.1.1')` throws `ERR_SOCKET_BAD_PORT`. Design lines 740-750 attach an error handler only to serverSocket.

**Fix:** Replace the parsing and connect code in design §3 with this text. "Parse the CONNECT target with a strict authority parser: `host:port` or `[v6]:port`. The port SHALL be a decimal integer from 1 to 65535 and is required; otherwise reply 400 and log it. Wrap the whole handler in try/catch and turn any exception into `502` plus a blockedLog entry. Never leave a rejected promise. Attach 'error' listeners to clientSocket and serverSocket before any await; each destroys both sockets. Set a 10 s connect timeout on serverSocket." Add a unit test that CONNECTs `example.test:443` with a fake resolver and asserts the tunnel opens, and one that resets the client mid-tunnel and asserts the process survives.

**Verifier note:** Reproduced on Node v24.11.1: `new URL('https://example.com:443/').port` is '' and `net.connect(NaN, ip)` throws ERR_SOCKET_BAD_PORT synchronously inside the async handler. Every port-443 CONNECT therefore becomes an unhandled rejection, and clientSocket has no 'error' listener.

## 5. [blocker] .kiro/specs/safe-fetch/design.md:237 (feasibility-integration)

**Issue:** The proxy is wired with a launch-level `--proxy-server` flag (clause 2.14; tasks.md task 12 adds it in buildLaunchArgs). That cannot work, for two reasons. (1) BrowserPool launches each browser once with buildLaunchArgs() and reuses it across concurrent audits for up to 50 sessions, so no per-audit proxy port can exist at launch time. (2) A raw `--proxy-server` arg skips Playwright's forced `<-loopback>` bypass rule, so Chromium's implicit bypass sends 127.0.0.1, localhost and [::1] DIRECT, around the guard.

**Evidence:** browser.ts:88-93: the pool launches with `chromium.launch({channel,args,headless})` from buildLaunchArgs(), and release() returns the browser to `idle` for reuse (MAX_SESSIONS_PER_BROWSER=50). playwright-core 1.65.1 coreBundle.js:40109-40114 (shouldProxyLoopback) adds '<-loopback>' only when the proxy comes from the `proxy` launch/context option (lines 40193-40202 and 40859-40866), never for a raw arg. Probe on this Windows machine (Playwright 1.65.1, channel chromium): launched with args ['--proxy-server=127.0.0.1:P'], page.goto('http://127.0.0.1:T/') loaded the page directly. The proxy log was empty, including for the page's `new WebSocket('ws://127.0.0.1:1')`. With `browser.newContext({ proxy: { server } })`, the same loopback GET and the ws CONNECT both reached the proxy.

**Fix:** Replace clause 2.14 with: "2.14 WHEN a restrictive audit begins THEN audit.ts SHALL start one SsrfGuardProxy for that audit on 127.0.0.1:0 and create the audit's BrowserContext with `browser.newContext({ ..., proxy: { server: 'http://127.0.0.1:<port>' } })` (Playwright context-level proxy). The pooled browser's launch args SHALL NOT change, and `--proxy-server` SHALL NOT be passed in `args`. The context proxy SHALL NOT set `bypass` (any loopback entry in bypass disables Playwright's forced `<-loopback>`, see shouldProxyLoopback)." In design §6 and tasks.md task 12, replace 'In buildLaunchArgs() accept proxyPort / add --proxy-server' with 'PageLoader.createContext(browser, options, egress?: { proxyServer: string }) passes `proxy: { server: egress.proxyServer }` to newContext; buildLaunchArgs is unchanged'. Add an integration test: under a restrictive audit, a page fetch to http://127.0.0.1:<other port>/ and a `new WebSocket('ws://127.0.0.1:<port>')` both appear in the proxy's log.

**Verifier note:** Confirmed. BrowserPool launches once with buildLaunchArgs() and reuses the browser, so a per-audit port cannot be set at launch. In playwright-core 1.65.1, coreBundle.js:40109-40114/40196/40863 adds '<-loopback>' only for the `proxy` option and never for a raw --proxy-server arg.

## 6. [blocker] .kiro/specs/safe-fetch/design.md:672 (feasibility-integration)

**Issue:** The proxy implements only the 'connect' event. Through an HTTP proxy, Chromium sends plain http:// requests as absolute-form `GET http://host/path` on the 'request' event, not as CONNECT. `http.createServer()` has no request listener, so every http:// navigation and subresource hangs until the navigation timeout. The spec has no plain-HTTP forwarding requirement at all, yet hosted audits must support http:// sites.

**Evidence:** Probe with a context-level proxy: the proxy log showed `HTTP GET http://127.0.0.1:65385/` (twice) for an http:// navigation, and `CONNECT example.invalid:443` only for https. Only ws:// arrived as CONNECT (`CONNECT ws.example.invalid:80`). design.md:672-673 registers only `this.server.on('connect', ...)`. The 'Proxy Flow' diagram (473-508) and task 11 describe CONNECT only.

**Fix:** Add clause 2.15a: "WHEN the proxy receives a non-CONNECT request THEN it SHALL require an absolute-form `http:` request-target (otherwise reply 400), resolve and validate the host exactly as in 2.15 (same pinned cache), and forward it with `http.request({ host: <hostname>, port, method, path: <origin-form path+query>, headers, lookup: pinnedLookup, agent: false })`. It SHALL strip `Proxy-Connection`, `Proxy-Authorization` and hop-by-hop headers, keep `Host`, and stream the request and response bodies both ways. It SHALL validate each request on a keep-alive client socket separately, because Chromium reuses one proxy connection for many hosts. It SHALL destroy the socket on any 'upgrade' event (Chromium sends WebSockets as CONNECT)." Add to task 11: 'register a request handler that forwards plain HTTP'. Add tests: plain-HTTP GET to an allowed host is forwarded with the body intact; a plain-HTTP GET to a blocked host is refused.

**Verifier note:** Confirmed. design.md:673 registers only server.on('connect'), and Chromium sends plain http:// through an HTTP proxy as absolute-form requests on the 'request' event, so nothing serves them.

## 7. [blocker] .kiro/specs/safe-fetch/design.md:704 (feasibility-integration)

**Issue:** For a CONNECT on the scheme's default port, the CONNECT target is parsed with `new URL('https://' + req.url + '/')` and then `parseInt(parsed.port)`. WHATWG URL drops a default port, so `example.com:443` gives port '' and parseInt gives NaN. `net.connect(NaN, ip)` then throws ERR_SOCKET_BAD_PORT synchronously inside the async 'connect' listener. That is an unhandled promise rejection, which terminates Node ≥15. The first https:// page any audit loads would crash the hosted server process.

**Evidence:** `new URL('https://example.com:443/').port` is '' and `parseInt('', 10)` is NaN. `net.connect(NaN, '93.184.216.34')` throws synchronously with code ERR_SOCKET_BAD_PORT (both verified with node v24.11.1). Chromium sends every https CONNECT as `host:443` (probe log: `CONNECT example.invalid:443`). design.md:673 binds an async handleConnect as an event listener, so nothing catches its rejection.

**Fix:** Replace the CONNECT parsing in §3 with: "Parse `req.url` as an authority with `/^(?:\[([0-9a-fA-F:.]+)\]|([^:\[\]]+)):(\d{1,5})$/`. Require an explicit port between 1 and 65535, and reply `400` and record 'invalid CONNECT target' otherwise. Do not use the URL constructor for CONNECT targets." Also add: "handleConnect and the request handler SHALL be wrapped as `(…args) => void this.handle(...args).catch(err => { destroy sockets; record 'proxy-error' })`, so no rejection escapes the event listener." Add a unit test: `CONNECT example.test:443` with a fake resolver returning 203.0.113.10 and a fake dial completes the tunnel.

**Verifier note:** Reproduced on node v24.11.1: new URL('https://example.com:443/').port is '', parseInt gives NaN, and net.connect(NaN, ip) throws ERR_SOCKET_BAD_PORT inside the async listener.

## 8. [blocker] .kiro/specs/safe-fetch/design.md:748 (feasibility-integration)

**Issue:** The tunnel never attaches an 'error' listener to clientSocket. Node removes its own socketOnError listener from a socket hijacked by 'connect', so the ECONNRESET that comes whenever Chromium tears down a context or tab mid-tunnel is thrown as an uncaught exception and crashes the process. The handler also does not destroy the peer socket when either side errors or closes.

**Evidence:** Probe: the design's handler body (net.connect, write 200, pipe both ways, error listener on serverSocket only) with a client that sends CONNECT and then calls resetAndDestroy() caused `UNCAUGHT (would crash the process): ECONNRESET read ECONNRESET`. In audit.ts, closeContext() runs at the end of every audit and on every timeout, which resets the open tunnels.

**Fix:** In §3, replace the connect/pipe block with: "Attach `clientSocket.on('error', destroyBoth)` and `serverSocket.on('error', destroyBoth)` before any await. Use `stream.pipeline(clientSocket, serverSocket, cb)` and `stream.pipeline(serverSocket, clientSocket, cb)`, where cb destroys both. If the upstream dial fails, write `HTTP/1.1 502 Bad Gateway\r\n\r\n` and then destroy the client socket." Add a unit test that resets the client mid-tunnel and asserts that the process emits no 'uncaughtException' (listen for the event in the test).

**Verifier note:** Reproduced the design's pipe pattern: the hijacked CONNECT socket has 0 'error' listeners, and a client reset caused an uncaught ECONNRESET.

## 9. [major] .kiro/specs/safe-fetch/design.md:216 (ssrf-completeness)

**Issue:** The range list still lets special-purpose addresses through. Clause 2.9 requires blocking IPv4-compatible `::/96`, but neither the IPv6 table nor isBlockedIPv6 implements it. Teredo `2001::/32`, local-use NAT64 `64:ff9b:1::/48`, site-local `fec0::/10`, discard `100::/64` and the documentation ranges `2001:db8::/32` and `3fff::/20` are all missing. On the IPv4 side, 192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24 and 192.88.99.0/24 are missing. security.md requires blocking 'any address that is not a globally routable unicast address', but the preservation test (design.md:1038) requires `http://203.0.113.42:8080/` to be ALLOWED.

**Evidence:** Verified: `new URL('http://[::127.0.0.1]/').hostname` is `[::7f00:1]`, and `dns.lookup('::127.0.0.1',{all:true,verbatim:true})` returns `[{address:'::127.0.0.1',family:6}]`. That address is not ::1/128 or ::/128, and isBlockedIPv6 (design.md:591) has no ::/96 branch, so it is allowed. The same holds for 2001:0:4136:e378:8000:63bf:3fff:fdd2 (Teredo) and 64:ff9b:1::a00:1.

**Fix:** Replace the deny lists in design 2.13 and task 9 with an allowlist that defaults to deny. "After `ipaddr.process()`: an IPv4 address is allowed only if `range() === 'unicast'`. An IPv6 address is allowed only if it is inside 2000::/3, `range() === 'unicast'`, and it is not in 2001::/23 (which includes Teredo 2001::/32), 2001:db8::/32, 2002::/16, 3fff::/20 or 5f00::/16. Exception: an address in 64:ff9b::/96 is allowed only if its low 32 bits, read as IPv4, pass the IPv4 rule. 64:ff9b:1::/48, ::/96, fec0::/10 and 100::/64 fall outside 2000::/3 and are therefore blocked." In the preservation tests and Example 5.1, replace 203.0.113.42 with a truly public address such as 93.184.215.14, and add 203.0.113.42 to the must-BLOCK cases.

**Verifier note:** Confirmed: `http://[::127.0.0.1]/` parses to `::7f00:1`, which matches no entry in BLOCKED_IPV6_RANGES and has no ::/96 branch in isBlockedIPv6 despite clause 2.9. Teredo, documentation and the other special ranges are also missing, and design.md:1038 requires the documentation address 203.0.113.42 to be allowed.

## 10. [major] .kiro/specs/safe-fetch/design.md:318 (ssrf-completeness)

**Issue:** Restrictive mode drops page.route (design 2.37; task 12 step 5 'no page.route() needed for restrictive mode'). That removes ResourceMeter.wrapPolicy, the only place requests are counted against MAX_REQUESTS (500) and the only place every request is refused once a limit is hit. An attacker page can then make unlimited requests through the proxy. The design also keeps a second blockedLog array (2.23) beside meter.blockedRequests, which the addendum forbids ('Do not duplicate the request counting').

**Evidence:** resource-limits.ts `wrapPolicy`: `this.usage.requestCount++; if (this.usage.requestCount > MAX_REQUESTS) this.breach(...)`, and `if (this.limit) return this.record(url, 'resource limit reached')`. This runs only when page.route calls shouldBlock. audit.ts:262 `blockedRequests: meter.blockedRequests`.

**Fix:** Amend 2.36, 2.37, task 12 and task 15. "In both modes installSafeFetchPolicy SHALL keep the page.route('**/*') handler using `meter.wrapPolicy(policy)` (counting, the scheme check and a fast pre-check). In restrictive mode the proxy is an additional, authoritative layer. The proxy SHALL write blocks through a callback that pushes into `meter.blockedRequests`, not into a separate array." Also note that page.route does not see redirect hops or WebSocket handshakes, so the proxy remains the enforcement point for those.

**Verifier note:** Confirmed: requestCount and the post-limit refusal exist only inside wrapPolicy (resource-limits.ts:48-52); the CDP attach() path records URLs and bytes but never counts requests. Removing page.route in restrictive mode (2.37, task 12 step 5) drops the MAX_REQUESTS limit, and 2.23 adds a second blocked log.

## 11. [major] .kiro/specs/safe-fetch/bugfix.md:145 (ssrf-completeness)

**Issue:** Expected-behavior clause 2.22 requires redirects to be intercepted in page.route(). Playwright never calls route handlers for redirect hops; it continues them automatically. An implementation that follows 2.22 literally still leaves every redirect bypass open. The clause also contradicts design 2.24-2.26, which relies on the proxy.

**Evidence:** In playwright-core 1.65.1 coreBundle.js (crNetworkManager._onRequest): `if (requestPausedEvent) { if (redirectedFrom || ...) { ... _sendMayFail("Fetch.continueRequest", ...) } }`. route2 stays null for every redirected request.

**Fix:** Replace bugfix.md 2.22 with: "WHEN a response redirects (301/302/303/307/308) THEN the follow-up request SHALL pass through the in-process proxy, which SHALL resolve, classify and pin the new target's host before any byte is sent to it. page.route is not relied on for redirect hops, because Playwright does not route them." Update 2.23 the same way.

**Verifier note:** Confirmed in coreBundle.js:37986-37992: a request with `redirectedFrom` is continued through Fetch.continueRequest with route2 left null, so page.route never sees redirect hops. Bugfix 2.22 as written cannot be met and contradicts design 2.24-2.26.

## 12. [major] .kiro/specs/safe-fetch/design.md:328 (ssrf-completeness)

**Issue:** auditHtml cannot work securely under the proxy, and the spec gives no way to make it work. auditHtml serves attacker-supplied HTML from http://127.0.0.1:<random port>. Once loopback goes through the proxy (required by the bypass-list fix), the proxy blocks the page itself. The only way the current spec 'works' for auditHtml (task 19 uses it) is the implicit loopback bypass. That same bypass lets the attacker's HTML reach every 127.0.0.1 port: the Fastify API, the proxy itself, and other local services.

**Evidence:** audit.ts:310-329 serves the HTML on 127.0.0.1:0 and wraps the policy in `OriginScopedPolicy(origin, ...)`. The proxy has no input that carries that exception. Task 19: 'Audit the HTML file using `auditHtml()` with `RestrictiveSafeFetchPolicy`'.

**Fix:** Add to design §3 and task 11: "SsrfGuardProxy SHALL accept `allowExact?: { host: '127.0.0.1'; port: number }`, set from OriginScopedPolicy by auditHtml. A request is exempt only if its target is exactly 127.0.0.1 and that port. The proxy dials it directly without DNS. Any other loopback host, port or encoding (localhost, 127.0.0.2, [::1], [::ffff:127.0.0.1]) SHALL be blocked." Add a test: auditHtml page whose script fetch()es http://127.0.0.1:<another live port>/ and http://localhost:<html port>/. Both must be blocked, and the HTML page must load.

**Verifier note:** Confirmed: auditHtml serves attacker HTML on 127.0.0.1 (audit.ts) and its OriginScopedPolicy exception lives only in the page.route policy, which restrictive mode drops. Today it works only through the implicit loopback bypass, which also exposes every local port, and the fix in [0] would block the page itself; the spec gives the proxy no way to carry the exception.

## 13. [major] .kiro/specs/safe-fetch/tasks.md:246 (ssrf-completeness)

**Issue:** A per-audit proxy port as a Chromium launch argument conflicts with the BrowserPool. Browsers are launched once (`chromium.launch(buildLaunchArgs())` with no arguments) and reused across audits. A restrictive audit can therefore get a pooled browser launched with no proxy, which connects directly and fails open. It can also get one pointing at a previous audit's proxy port, which is stopped or now bound by another audit's proxy, so blocks and pinning go to the wrong audit.

**Evidence:** browser.ts:88-92 `options.launch ?? (() => { const { channel, args, headless } = buildLaunchArgs(); return chromium.launch(...) })`. The pool reuses browsers (audit-engine-reverify-1.md: 'the browser stays in the pool for up to 50 sessions'). Task 12 says 'In buildLaunchArgs(), accept proxyPort' and 'Acquire browser with proxyPort passed to launch args'. Design §6 admits 'This requires refactoring browser.ts'.

**Fix:** Replace task 12's browser.ts bullets with: "Do not change buildLaunchArgs for the proxy. Pass the proxy per context: `PageLoader.createContext(browser, options, proxy?: { server: string; bypass: '<-loopback>' })` forwards it to `browser.newContext({ proxy })`. auditUrl starts the proxy before createContext and stops it after closeContext in the same finally block." Add a test with a pool of maxConcurrency 1 running two sequential restrictive audits; the second must use its own proxy, checked by a blocked-log entry appearing only in the second audit.

**Verifier note:** Confirmed: BrowserPool launches with a no-argument `buildLaunchArgs()` (browser.ts:88-92) and reuses browsers for up to 50 sessions. Task 12's per-audit `proxyPort` launch argument therefore cannot reach a pooled browser, or points at a stale proxy port.

## 14. [major] .kiro/specs/safe-fetch/design.md:264 (ssrf-completeness)

**Issue:** Lookups have no timeout and no limit. Clause 2.20 promises a 5 s DNS timeout, but resolveHostname (line 529) awaits `dns.lookup` with no timeout. dns.lookup runs on libuv's threadpool, which has 4 threads by default. An attacker page that references many unique hostnames served by a slow authoritative DNS can pin every threadpool thread. That stalls DNS, fs and crypto for all concurrent audits and the API server. A timeout that only races the promise still leaves the threads occupied.

**Evidence:** design.md:527-533 shows `results = await lookup(hostname, { all: true, verbatim: true })` with no timer. No per-audit limit on lookups or unique hosts appears anywhere in design.md or tasks.md.

**Fix:** Add to design 2.20 and task 10: "resolveHostname SHALL reject with 'DNS resolution timed out' after 5 s, and the request SHALL be blocked. Lookups SHALL go through a process-wide semaphore of at most 2 concurrent lookups per audit and 4 in total. Each audit SHALL resolve at most 100 distinct hostnames; beyond that every new hostname is blocked with reason 'hostname limit reached'. A cached hostname needs no lookup." Add fake-resolver tests for a never-settling lookup, which must block within 5 s, and for the 101st host, which must be blocked.

**Verifier note:** Confirmed: clause 2.20 and task 12 promise a 5 s DNS timeout, but resolveHostname (design.md:527-533) awaits lookup with no timer. No per-audit or process-wide cap on getaddrinfo calls exists either, so a page can tie up libuv's 4 threadpool threads.

## 15. [major] .kiro/specs/safe-fetch/design.md:292 (ssrf-completeness)

**Issue:** The WebRTC control does not exist. `--disable-webrtc` is not a Chromium switch, so Chromium ignores it. Bugfix 6.2 says 'no Chromium launch flags disable WebRTC', but buildLaunchArgs already applies real flags. Tasks 6, 13 and 19 assert only that the string is present, so they pass whatever the browser does. Someone tidying up flags could also remove the real WEBRTC_LEAK_FLAGS. The prompt said to reference the existing flags.

**Fix:** Replace design 2.29, bugfix 2.25 and task 13 with: "Chromium SHALL keep `WEBRTC_LEAK_FLAGS` from browser.ts (`--force-webrtc-ip-handling-policy=disable_non_proxied_udp`). With the proxy in place, WebRTC can only use TCP through the proxy's CONNECT, which is validated." Delete bugfix 6.2's claim.
